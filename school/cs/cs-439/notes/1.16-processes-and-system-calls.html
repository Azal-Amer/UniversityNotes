Now inside the kernel there is a node and a StrongRef to Node. Open returns our node
What we're going to do is never leak direct kernel information back into user code. No pointer ever crosses over
PCB: Process control block. We're going to have a pointer to a set of references for all the files the user owns
We look for the null entry in the array which belongs to the user itself, we get the number in said array and return the index in that array. The user passes in the index for the array. That index points to the node. The only way to put something there is if the user opens it, so anything they request is valid.
Diagram of our user system

CLOSE just removes us from the FDT! If it's a StrongRef we just set it to null and the destructor does its works.

What should the user read do?
People observed really quickly that most of the time people read and write sequentially. It occurs with very high probability. Pretty much all programming languages optimize for this case.
read(fd,buffer,length). We give the user as much as we want, no promises, but no offset.

  • The kernel maintains the offset. it keeps track of where we are in the file, so we read from the next place.
    To do that we keep an intermediate file structure to a spot in the FDT which keeps track of the current offset.
  • In there we can store permissions! That's metadata for the open file
    We also have a seek function
    seek(fd,....., whence) whence tells us how to interpret the offset.
    Most system calls you can get in a few minutes if you did your job right.
  • Just update the intermediate file structure offset
